## 三、核心亮点（面试深挖点）

### 1. 秒杀高并发治理（主打故事，压测数据支撑）

**分层拦截漏斗**（越靠前成本越低）：

```
IP/用户两级限流(Lua固定窗口) → 本地售罄标记(O(1)拒绝)
→ Caffeine 元数据缓存(场次/券/商品，空值防穿透)
→ Redis Lua 原子抢购(判重+扣减+记录，1次RTT)
→ 编程式事务落库(仅DB段，扣库存原子UPDATE)
→ 失败补偿(Redis抢占回滚 rollbackClaim)
```

- **Redis Lua 原子化**：判重 SISMEMBER + 扣减 DECR + 记录 SADD 三次往返合并为 1 次脚本执行，
  消除竞态窗口，库存不足在脚本内回补；
- **事务收窄**：`@Transactional` 移出主流程，仅落库段用 `TransactionTemplate` 包裹——
  被拒绝的请求不再借出 DB 连接，连接池不被无效流量挤占；
- **限流器**：修复 `INCR+EXPIRE` 两步执行的"计数键永不过期"竞态，改为原子 Lua；
- **压测方法**：固定变量法（同机同参同数据）、JIT 预热、时间分桶看稳态 QPS、
  **jstack 线程转储定位真实阻塞点**（见第 2 点）。

### 2. jstack 实战排查案例（区分度最高的故事）

压测发现吞吐卡在 ~200 QPS，但 68/104 个 Tomcat 线程是空闲的——**瓶颈不在业务**。
抓线程转储发现 35 个线程阻塞在 `ServiceLoader → JarURLConnection`：

- **根因**：jjwt 每次构建 parser 都会扫描全 classpath 的 `META-INF/services/`
  （逐个打开 100+ JAR，内部 `JarFileFactory` 有同步锁），而代码每个请求构建 4~5 次 parser；
- **修复**：parser 构建一次全局复用（不可变、线程安全），签名校验语义不变；
- **验证**：单请求成本 46ms → 23ms，吞吐 +54%；
- **面试价值**：证明"用证据定位问题而不是猜"的工程习惯，且这是 jjwt 官方文档警示的反模式。

### 3. 搜索可用性设计：ES 开关 + MySQL 降级

- `elasticsearch.enabled` 一键切换；无 ES 环境自动降级 MySQL LIKE 搜索；
- 排序口径统一：无关键词按 id 升序（新品优先），有关键词时 ES 走 `_score` 相关性；
- 面试价值：体现"外部依赖故障不影响核心链路"的降级思维。

### 4. RabbitMQ 异步化与可靠性

- 订单超时取消：延迟消息插件（`x-delayed-message`），下单即投递，到期消费关单，轮询 DB 的方案被替代；
- 访问日志：Filter 内投递 MQ，消费端落库，请求线程零阻塞；
- 邮件发送异步化，失败不影响主流程。

### 5. Redis 缓存体系（穿透/击穿/雪崩防护）

- 空值缓存 + Optional 包装防穿透；短 TTL 本地缓存（Caffeine）挡住热点元数据查询；
- 缓存与 DB 双写一致性：元数据变更主动失效（本地 + Redis 同步清理）；
- 详见 `docs/Redis缓存穿透击穿雪崩详解.md`（如存在）。

### 6. 工程化与部署

- Docker / docker-compose 一键部署；Nginx 反向代理（`/prod-api` 前缀剥离、SSE 长连接
  `proxy_buffering off` + 3600s 读超时）；
- 环境隔离：application-dev/docker/prod 三套配置；
- 压测脚本化：prepare / reset / jmx 全参数化，**任何人可一键复现报告数据**。

### 7. 前端体验（全栈广度）

- 高频页面 keep-alive 缓存：滚动位置 sessionStorage 持久化恢复、onActivated 刷新 / onDeactivated 暂停定时器；
- 商家端列表编辑后保持分页状态（MerchantLayout keep-alive include 方案）；
- 移动端适配（秒杀卡片纵向布局、底部 Tab 避让）与暗色模式。

### 8. 支付链路：真实联调 + 对账自愈

- 支付宝沙箱全流程：下单 → 手机沙箱支付 → return-url 回跳结果页（前端注册 `/pay/result` 路由 + 倒计时返回订单页）；
- **对账自愈设计**：本地未配内网穿透时主动放弃异步回调，改为结果页轮询 `alipay.trade.query`，
  确认 `TRADE_SUCCESS` 后调对账入账接口——回调与轮询两条路径最终都收敛到同一核心入账逻辑 `payOrder`
  （改状态/记支付时间/加销量/发 MQ 扣库存与商家通知/拼团成团判定），幂等保护防重复入账；
- 支付方式一致性：订单落库 `pay_method`，收银台预选、改选回写、支付后锁定；
- 联调踩坑实录（面试好素材）：Spring 配置优先级导致环境变量覆盖 yml 密钥、配置文件外置明文密钥、
  return-url 必须是线上地址而非 localhost。

### 9. AI 能力三件套（独立 Python 微服务）

- 架构：FastAPI 独立服务（:5000），Nginx/Vite 以 `/ai` 前缀反代，与 Java 主服务解耦；
- **AI 客服 + RAG**：知识库文档切分 → 通义 text-embedding-v3 向量化 → 余弦相似度线性检索
  （TOP_K=3 + 阈值 0.7 过滤）→ 命中条目带分类标签注入 system prompt → qwen-turbo 生成；
  **防幻觉硬约束**：检索为空时在提示词中禁止模型使用库外知识，实测"问天气"明确拒答不编造；
- 商家端 AI 一键生成商品介绍：卖点短句 + 详情文案 + SEO 关键词，JSON 结构化输出（含 ```json 围栏容错解析）；
- 后台 AI 评论情感分析：批量分析 + 分批容错（单批失败不阻塞），正/负/中性标签 + 关键点提取；
- Function Calling（客服订单工具）与 RAG 检索并存：工具查实时数据，RAG 答静态知识。

### 10. 商品关联推荐（业务补全 + 缓存取舍）

- 详情页"相似商品 / 同店热销"：同分类、同商家两条查询，排除自身、只在售、按销量+评分排序，
  **跨分组去重**（同店热销多取 N 条再截断），同类不足时宁缺毋滥不做全站兜底；
- **故意不加 Redis 缓存**（面试可主动讲的取舍）：推荐排序依赖 sales/avgRating/status 高频写字段，
  失效点散落在支付、商品管理、拼团、评论 5+ 处，按商品维度缓存 key 基数大命中率低；
  若要加应缓存"分类/商家维度榜单"（key 数可控）+ 内存过滤当前商品，TTL 对齐热销榜；
- PC 与移动端共用同构组件，断点适配两列网格。

### 11. 数据一致性治理：修数据 + 修代码（闭环思维）

- **现象**：测试数据污染 + 商家编辑商品后 SKU 销量清零，`product.sales ≠ SUM(sku.sales)`，
  且大量商品 SKU specs 与规格模板失配（详情页规格选择器整体消失）；
- **修数据**：幂等 SQL 修复脚本（预览→备份→修复→验证四段式）：以 SKU 为准回写销量/库存、
  无模板商品从 SKU 反推生成规格模板、补键合并重复组合、补齐 588 个"模板有值但无 SKU"的死组合；
  全程销量/库存守恒，四张备份表可回滚，重复执行零副作用；
- **修代码（根因）**：商家编辑走"先删后增"重插 SKU 时不回填销量——修复为先按**规格内容规范化键**
  （JSON 解析后按键排序，兼容前后端键序差异）缓存旧销量，重插时回填；改规格名导致无法匹配的
  旧销量兜底归属第一条新 SKU，总销量守恒不变；
- **面试价值**：展示"对账发现 → 定位写入路径根因 → 数据修复 + 代码修复 + 幂等防复发"的完整闭环，
  以及"宁缺毋滥"（死组合补 stock=0 占位而非删除模板值）的产品思维。

## 四、面试高频追问 Q&A

**Q1：怎么保证秒杀不超卖？**
三层防线：① Redis Lua 脚本内 `DECR` 判负即回补拒绝（原子，无竞态）；② DB 落库用
`UPDATE ... SET stock=stock-1 WHERE stock>0` 原子扣减（条件更新，影响行数为 0 即售罄）；
③ 发放记录以 Redis 用户集合判重。压测后三方对账：库存扣减数 = 发放券数 = 去重用户数。

**Q2：Redis 扣减成功但 DB 写入失败怎么办？**
catch 中执行补偿回滚：Redis 库存 INCR 回补 + 用户集合 SREM，事务由 TransactionTemplate 回滚，
最终一致性由补偿保证。（追问"极端宕机丢补偿"可答：库存以 DB 为准做对账修复任务，Redis 仅是加速层。）

**Q3：为什么 QPS 只提升 68% 而不是 10 倍？**
测试机同时承载 JMeter 客户端、MySQL、Redis、MQ 与前后端服务，CPU 有上限；
优化后 seckill 路径已与公共链路（TraceFilter 每请求发 MQ 日志）持平，瓶颈转移——
这本身就是压测结论之一，下一步优化公共链路。（体现对数据诚实、知道瓶颈在哪）

**Q4：怎么发现 JWT 那个瓶颈的？**
压测中 QPS 与线程活跃度对不上（大量线程空闲），抓 jstack 看真实阻塞点，
发现线程在 `ServiceLoader` 开 JAR 文件。定位到 jjwt 每次构建 parser 都扫描
`META-INF/services`，而代码每请求构建 4~5 次。改为全局复用即可。
——强调方法论：**先看线程在哪等，再改代码**。

**Q5：事务为什么不用 @Transactional？**
注解在主流程上会让 98% 的拒绝请求也借连接开空事务，连接池被打满。
编程式事务只包 DB 段，拒绝路径零 DB 成本。代价是代码略冗长，
但秒杀这种"拒绝流量远大于成功流量"的场景必须收窄。

**Q6：如果 QPS 再涨 10 倍怎么办？**（架构演进题）
限流前置（网关层）→ 库存分桶（拆 Redis 大 key）→ 削峰填谷（MQ 异步落库，
前端排队/令牌桶）→ 读写分离/缓存多级 → 无状态水平扩容。说明当前单机方案的天花板与演进路径。

**Q7：支付宝异步回调没收到，订单就一直不入账吗？**
不是。回调只是加速路径：结果页会轮询 `alipay.trade.query`，确认 `TRADE_SUCCESS` 后走对账入账
（与回调收敛到同一个带幂等保护的 `payOrder`）。回调和对账两条路径都存在时，靠幂等（订单状态机 +
支付流水唯一）保证只入账一次。这是"外部依赖不可靠时，用主动对账兜底最终一致性"的思路。

**Q8：商品推荐为什么故意不加 Redis 缓存？**
推荐排序依赖销量/评分/状态这些高频写字段，失效点散落在支付、商品管理、拼团、评论多个模块，
按商品维度缓存（key 基数大）一致性维护成本高于两条带索引的单表查询收益。真要加我会缓存
分类/商家维度的榜单（key 数 = 分类/商家数，可控），商品过滤和去重放内存。**加不加缓存是收益
和一致性的权衡，不是惯例**。

**Q9：测试数据把销量弄脏了怎么处理？**
先对账（SQL 找出 product.sales 与 SUM(sku.sales) 不一致的行），再双向修：数据侧用幂等脚本
（预览→备份→修复→验证，可重复执行、可回滚）以 SKU 为准回写；代码侧定位到商家编辑"先删后增
不回填销量"的根因并修复（规格内容规范化匹配 + 总量守恒兜底）。只修数据不修代码会复发，
只修代码不修数据线上仍是脏的。
