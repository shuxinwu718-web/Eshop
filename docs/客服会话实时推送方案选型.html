Section 01

现状：为什么沟通慢

用户只能发一次留言、商家回一次，且双方都没有实时通道。

数据模型是"单轮问答"，不是会话

merchant_message 一行记录 = 用户留言 + 一个 reply_content / reply_time。商家回复一次后这条就结束了，用户想追问只能再发一条新留言。表里没有 conversation（会话）概念，也没有消息序列，因此无法承载连续对话。

双方都没有实时通道

商家回复时，只会写一条站内通知（NoticeService.createAndPublish），用户端的未读数靠前端 30 秒轮询兜底，且这个间隔被硬编码在三个文件里。用户体验上表现为"问完要等，回完不知道"。

消息从服务端到客户端的三种老办法

要让服务端主动把新消息送到浏览器，只有三条路：客户端反复问（轮询）、等客户端的问（长轮询）、或者干脆不让客户端问（服务端推送）。前两条属于"客户端拉动"，本质没变，只是节奏不同。

两种轮询都不改变"客户端拉动"的本质：间隔长则慢，间隔短则服务端被无效请求打满。真正让服务端"主动说话"的技术，只有 SSE 与 WebSocket。
Section 02

方案一：SSE 长连接

一次普通 HTTP 请求，换回一条服务端可以随时往里写数据的连接。

SSE（Server-Sent Events）建立在 HTTP 之上：浏览器用 EventSource 发起一个 GET 请求，服务端返回 Content-Type: text/event-stream 之后不结束响应，而是保持这条连接打开。此后服务端随时可以按固定格式写入一段文本，浏览器对应的监听函数立刻被触发。

四个必须记住的特性

  • 半双工：这条连接只能服务端 → 客户端单向推。客户端要发消息，得另发一个普通 POST，反而能直接复用现有的目录、鉴权和错误码体系。
  • 断线自动重连：EventSource 浏览器内建重试，不需要自己写重连逻辑（对比 WebSocket 需要自己实现）。
  • 鉴权只能放 URL：EventSource 不支持自定义请求头，没法带 Authorization: Bearer，所以 token 只能拼在 query 上，由后端在建立连接时校验。这也是本项目 SseController 已经在用的做法。
  • Nginx 必须关缓冲：反向代理默认会缓冲响应，导致事件被攒着一起发。需要 proxy_buffering off 与足够长的 proxy_read_timeout。本项目生产环境已经配好。
报文格式很简单：一段事件形如 event: notice + 换行 + data: {...} + 空行，以空行作为一条事件的结束标志。
Section 03

方案二：WebSocket

先用 HTTP 完成握手，再把这条连接升级成双向帧通道。

WebSocket 的起点仍然是一个 HTTP 请求，只是带了 Upgrade: websocket 头；服务端同意后回复 101 Switching Protocols，这条 TCP 连接从此脱离 HTTP 语义，变成双方都能随时发送数据帧的通道。这正是它比 SSE 强的地方，也是它复杂的地方。

带来能力，也带来四项额外工作

  • 心跳保活：链路上任何一环（运营商、Nginx、防火墙）都可能悄悄掐掉空闲连接，必须自己实现 ping / pong 定时探测。
  • 断线重连：浏览器 API 不会自动重连，要自己写重连与退避策略，还要考虑断线期间漏掉的消息如何补偿。
  • 鉴权更难：浏览器原生 WebSocket API 同样不能设置请求头，需要在 STOMP 的 CONNECT 帧里带 token，并用 ChannelInterceptor 校验，或退化成 URL 带 token。
  • 新增依赖与运维：需要引入 spring-boot-starter-websocket（本项目目前完全没有 WebSocket 依赖），并在 Nginx 上透传 Upgrade / Connection 头。项目也不存在任何 WebSocket 配置类，等于从零搭。

Section 05

三个关键判断

选型要看的不是"哪个技术更强"，而是"哪个更匹配这个场景与这台机器"。

判断一：半双工对"客服对话"不是硬伤

SSE 只能服务端单向推，客户端发消息要另发 POST。放进客服场景就不构成问题：对话节奏是"一问一答"，不是毫秒级双向同步——收消息必须实时（这正是当前痛点），而发消息用一次普通 POST 反而顺带获得了 HTTP 的鉴权、日志、错误码能力，比在 WS 帧里自己约定协议更省事。

判断二：2 核 2G 单机上，两者都能跑，差在维护面

通道 每连接主要成本 100 并发在线的量级 实际压力
SSE 一个 SseEmitter + 异步 Servlet 请求对象 + socket 缓冲；异步模式不占 Tomcat 工作线程 堆上约几 MB 后端堆为 -Xmx512m，占比可忽略；真正上限是 maxConnections（Tomcat 默认 8192）
WebSocket WebSocketSession + STOMP 帧缓冲 + 心跳任务，通常还需要额外的调度/心跳线程 略高于 SSE 仍能承载，但需留意 2G 机器的 GC 压力与心跳线程开销

真正的差别不在"能不能跑"，而在出问题时要同时排查几个地方：SSE 是 HTTP 语义的延续，能用 Nginx 日志和浏览器 Network 面板直接看；WebSocket 一旦连不上，要同时怀疑握手、Upgrade 透传、STOMP 拦截器、心跳四件事。

判断三：学习收益各有侧重

走 SSE 会掌握 走 WebSocket 会掌握
HTTP 长连接与 Servlet 异步模型HTTP Upgrade 协议切换（101）
SseEmitter 生命周期：onCompletion/onTimeout/onError帧协议与文本流的区别、全双工通信
text/event-stream 报文格式与 EventSource API心跳保活 ping/pong 与超时判定
为什么鉴权要放 URL（EventSource 不能设 Header）STOMP 子协议与 ChannelInterceptor 做 JWT 鉴权
Nginx 反代长连接：proxy_buffering offNginx Upgrade 头透传配置
"按 userId 定向推送"的连接注册表设计离线消息补偿、消息可靠投递
单实例内存态的局限 → 何时该上 Redis Pub/Sub集群会话共享与消息路由
建议路径：先用 SSE 落地，把实时链路真正跑通（目前前端 setupSse() 无人调用、整条链路是死代码，先接通本身就是一次很好的学习）；理解"推送"的本质之后，再把通道替换成 WebSocket 做进阶，此时是"知道为什么换"而不是"照教程抄一遍"。
