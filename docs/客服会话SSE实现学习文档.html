Chapter 1 · 架构层

SSE 协议原理：HTTP 层发生了什么

SSE 没有任何魔法——它就是一个「永远不返回结束」的普通 HTTP 响应，服务端往里不断追加文本。

1.1 一次握手，无限响应

浏览器发一个普通 GET 请求，服务端返回特定响应头后不关连接，之后随时往响应体里写数据：

图 1 · SSE = 一个不结束的 HTTP 响应。①② 只发生一次，③④⑤ 由服务端按需推送。

1.2 报文格式：只有 4 个字段

响应体里每条消息就是一段纯文本，空行表示一条消息结束。字段全部以 key: value 形式书写：

一条完整的 SSE 消息（协议原文）text/event-stream
# event：事件类型。省略时默认为 message（前端 onmessage 才能收到）
event: im-message
# data：消息内容，前端拿到的 event.data 就是它（一般放 JSON 字符串）
data: {"msgId":1001,"content":"您好，在的","senderId":2}
# id：消息编号。断线重连时浏览器自动带上 Last-Event-ID 头，可用于补发
id: 1001
# retry：告诉浏览器断线后隔多少毫秒重连
retry: 3000
# ← 这里必须是空行，代表消息结束，浏览器此时才触发监听器
字段作用不写会怎样
data消息本体，唯一必需字段消息无效
event事件类型，前端按名监听归入默认 message 事件
id断线重连续传的游标重连后从最新开始，不补发
retry自动重连间隔(ms)浏览器用默认值（约 3 秒）

1.3 浏览器 EventSource 的三个关键行为

  1. 自动重连：连接断了（网络抖动、服务重启），浏览器自动按 retry 间隔重连，前端几乎不用写重连逻辑。这是 SSE 相对 WebSocket 最大的省心点。
  2. 只能 GET、不能自定义 Header：new EventSource(url) 不支持设置 Authorization 头 → 所以本项目把 JWT 放在 URL 的 ?token= 里（第 4 章详述）。
  3. 同源/跨域受 CORS 约束：本项目前端走 Nginx 同源反代（/prod-api 前缀），不存在跨域问题。

1.4 半双工：发消息为什么仍走普通 POST

SSE 通道是单向的（仅服务端→客户端）。用户 A 给 B 发消息时，前端走的仍是普通 REST 请求：

发消息 vs 收消息，走两条不同的路设计约定
发消息（上行）：POST /api/v1/chat/messages   ← 普通 REST，带 Authorization 头，Spring Security 正常鉴权
收消息（下行）：GET  /api/v1/sse/connect      ← SSE 长连接，token 在 URL，事件名 im-message 推给你
这与项目现有惯例完全一致：现有 SSE 也只负责下行（广播 online-count），所有普通业务都是 REST。WebSocket 方案里上行也要走帧通道，那才是它的复杂度来源之一。

Chapter 2 · 后端代码层

SseEmitter 与现有 SseController 逐行解析

文件：src/main/java/com/shopsphere/eshop/controller/SseController.java（全文 108 行，本项目唯一的 SSE 实现）。

2.1 SseEmitter 是什么

SseEmitter 是 Spring MVC 对 Servlet 3.0 异步响应的封装。Controller 方法直接 return emitter，Spring 会：

  1. 立刻释放 Tomcat 工作线程（线程回池子继续服务别的请求，这就是长连接不吃并发线程数的原因）；
  2. 保持 HTTP 连接和响应流打开；
  3. 之后任何线程调用 emitter.send(...) 都会往这条响应流写一条 SSE 消息。
为什么 2C2G 扛得住：每条 SSE 连接 ≈ 1 个 socket + 少量内存，不占工作线程。几百条在线连接的内存开销可忽略，这正是选型文档判断「2 核 2G 可用」的依据。

2.2 成员变量：连接注册表

SseController.java · L34-35Java
// 连接注册表：key = "userId_时间戳"，value = 这条连接的 emitter
private final Map<String, SseEmitter> emitters = new ConcurrentHashMap<>();
// 单线程调度器：负责每 5 秒广播在线人数（等效心跳）
private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
  • ConcurrentHashMap：SSE 回调（onTimeout/onError）和心跳线程在不同线程里增删 map，必须线程安全。
  • 局限：key 是「用户id_时间戳」，值只有单个 emitter——想「给某个用户推消息」时，得遍历全 map 解析 key 前缀，且一个用户开 3 个 Tab 就有 3 条散落记录。改造目标是 Map<Long, Set<SseEmitter>>（见 6.2）。

2.3 connect()：建立连接的完整流程

SseController.java · L37-89（节选，含行号）Java
@GetMapping(value = "/connect", produces = MediaType.TEXT_EVENT_STREAM_VALUE)  // ① 声明响应类型
public SseEmitter connect(@RequestParam String token, @CurrentUserId Long userId) {  // ② 双通道鉴权
    String username;
    try {
        username = jwtUtil.getUsernameFromToken(token);   // ③ 手动再验一次 URL 里的 token
    } catch (Exception e) {
        // token 无效：造一个立即关闭的 emitter，浏览器收到 error 事件后不再重连（complete 了）
        SseEmitter errorEmitter = new SseEmitter(0L);
        errorEmitter.send(SseEmitter.event().name("error").data("Token验证失败: " + e.getMessage()));
        errorEmitter.complete();
        return errorEmitter;
    }
    onlineUserService.updateHeartbeat(userId, username);  // ④ 记录在线状态（管理端看在线人数用）

    SseEmitter emitter = new SseEmitter(3600000L);        // ⑤ 超时 1 小时，到点触发 onTimeout
    String emitterId = userId + "_" + System.currentTimeMillis();  // ⑥ 唯一键
    emitters.put(emitterId, emitter);

    emitter.send(SseEmitter.event()                       // ⑦ 立刻推一条初始数据
            .name("online-count")
            .data(String.valueOf(onlineUserService.getOnlineCount())));

    emitter.onCompletion(() -> emitters.remove(emitterId));  // ⑧ 三个生命周期回调：
    emitter.onTimeout(()   -> emitters.remove(emitterId));  //    正常关闭 / 超时 / IO错误
    emitter.onError(e      -> emitters.remove(emitterId));  //    任一触发都要从 map 移除，防泄漏
    return emitter;                                        // ⑨ 交回 Spring，线程立即释放
}

三个必须理解的设计点：

  1. produces = TEXT_EVENT_STREAM_VALUE：让 Spring 写出 Content-Type: text/event-stream，浏览器 EventSource 才认。
  2. 鉴权是「双保险」：SecurityConfig 把 /api/v1/sse/** 放进了 permitAll（因为 EventSource 带不了 Header，见第 4 章），所以这个方法必须自己校验 token；参数里的 userId 由参数解析器从 Authorization 头解析（页面正常登录时有），token 则来自 URL query（EventSource 用）。
  3. 回调即善后：连接断开的三种方式（正常关/超时/出错）都必须把 emitter 从 map 移除。漏写 = map 里堆死连接 = 每次广播都在对空气 send + 抛 IOException。

2.4 init()：每 5 秒的心跳广播线程

SseController.java · L91-107Java
@PostConstruct   // Bean 创建完成后执行一次，启动广播任务
public void init() {
    scheduler.scheduleAtFixedRate(() -> {
        int count = onlineUserService.getOnlineCount();
        emitters.entrySet().removeIf(entry -> {       // 遍历所有连接
            try {
                entry.getValue().send(SseEmitter.event()
                        .name("online-count")
                        .data(String.valueOf(count)));
                return false;                          // 发送成功：保留
            } catch (IOException e) {
                return true;                           // 发送失败 = 连接已断：顺手移除
            }
        });
    }, 5, 5, TimeUnit.SECONDS);                        // 首次延迟 5s，之后每 5s 一次
}

这段代码身兼两职：

  • 业务：管理端在线人数实时刷新；
  • 心跳：每 5 秒必有一次数据流动，防止 Nginx / 防火墙把「长时间静默」的连接当死连接掐掉。改造后必须保留这个心跳职责（或改为专用的 event: ping）。
线程模型提醒：所有 emitter.send() 都可能被多个线程（心跳线程 + 业务推送线程）并发调用。Spring 的 SseEmitter.send 本身做了同步保护，但「遍历 + 移除」必须像上面一样用 removeIf 或 ConcurrentHashMap 的安全操作，不能用普通 for + remove。

Chapter 3 · 前端代码层

useSse.ts 逐行解析与两个断点

文件：前端仓库 src/composables/sse/useSse.ts（全文 269 行，原生 EventSource 的单例封装）。

3.1 单例模式：全站只有一条 SSE 连接

useSse.ts · L26 + L247-252TypeScript
// 模块级变量：整个应用生命周期的唯一实例
let globalInstance: ReturnType<typeof createSseConnection> | null = null;

export function useSse(options: UseSseOptions = {}) {
  if (!globalInstance) {
    globalInstance = createSseConnection(options);   // 第一次调用才创建
  }
  return globalInstance;                             // 之后所有调用者共享同一实例
}

为什么要单例：一条 SSE 连接对服务端是一条内存记录 + 一个 socket。如果 10 个组件各自 new EventSource，服务端会记 10 条连接，心跳也广播 10 份。正确姿势是「一条连接 + 多个订阅者」——这正是下面事件注册表的作用。

3.2 connect()：token 拼 URL + 建立连接

useSse.ts · L125-171（节选）TypeScript
const connect = () => {
  isManualDisconnect = false;                        // 重置手动断开标志
  if (eventSource && connectionState.value === SseConnectionState.CONNECTED) return;  // 防重复连
  if (connectionState.value === SseConnectionState.CONNECTING) return;

  const token = AuthStorage.getAccessToken();
  if (!token) return;                                // 未登录直接不连（游客不发请求）

  connectionState.value = SseConnectionState.CONNECTING;
  // URL 形如 /prod-api/api/v1/sse/connect?token=eyJhbGci...（走 Nginx 反代，同源）
  const baseApi = import.meta.env.VITE_APP_BASE_API || "/dev-api";
  const fullUrl = `${baseApi}/api/v1/sse/connect?token=${encodeURIComponent(token)}`;
  eventSource = new EventSource(fullUrl);

  // 10 秒连不上则主动断开（connectionTimeout 默认 10000ms），避免半死连接
  connectionTimeoutTimer = setTimeout(() => {
    if (connectionState.value === SseConnectionState.CONNECTING) disconnect();
  }, config.connectionTimeout);

  eventSource.onopen  = handleOpen;    // 状态 → CONNECTED，清超时定时器
  eventSource.onerror = handleError;   // 状态 → DISCONNECTED；非手动断开时浏览器自动重连
  eventSource.onmessage = handleMessage; // 只接 event 字段缺省的 message 事件
};

3.3 事件注册表：一条连接分发多种业务

useSse.ts · L180-204（on 方法）TypeScript
const eventHandlers = new Map<string, Set<EventHandler>>();  // 事件名 → 一组回调

const on = (eventName: string, handler: EventHandler): (() => void) => {
  if (!eventHandlers.has(eventName)) eventHandlers.set(eventName, new Set());
  eventHandlers.get(eventName)!.add(handler);

  // 关键：非 message 事件必须用 addEventListener 按名注册到 EventSource 上
  // （对应服务端 SseEmitter.event().name("xxx") 写出的 event: xxx 行）
  if (eventName !== "message" && eventSource) {
    eventSource.addEventListener(eventName, handleCustomEvent(eventName) as EventListener);
  }
  return () => { ... };   // 返回取消订阅函数——组件 onBeforeUnmount 时调用防泄漏
};

分发流程：浏览器收到 event: online-count → 触发同名 listener → handleCustomEvent("online-count") 里 JSON.parse(event.data)（失败则原文透传）→ 逐个调用注册表里的 handler。新加一种推送（如 im-message），useSse 一行都不用改，新 composable 里 on("im-message", ...) 即可。

3.4 发现的两个「断点」（本次改造要接上的线）

  1. setupSse() 无人调用：src/composables/sse/index.ts 定义了统一的初始化入口 setupSse()（内部调 dictSync/onlineCount 的 initialize → 最终调 sse.connect()），但全仓 grep 不到任何调用点——main.ts 没调、布局组件也没调。SSE 链路目前整体是死代码，浏览器从未真正连过。
  2. useNotice 订阅了永远不会来的事件：src/components/NoticeDropdown/useNotice.ts L73/L105 订阅了 notice、notice-revoke 两个事件，但后端全仓没有任何 name("notice") 的推送代码。前端逻辑写好了，生产者缺失——改造时把 NoticeService 的事件接上 sendToUser，这套代码立即活过来。
学习点：排查「实时功能不工作」时，先画清三段链路——生产者（后端谁调 sendToUser）→ 通道（SseEmitter/EventSource 是否连上）→ 消费者（前端谁 on 了事件名）。本案是三段都各缺一刀：生产者没有 sendToUser、通道没有 connect、消费者等不到事件。事件名必须两端严格一致（online-count 带连字符，写错大小写都收不到）。

3.5 参照范式：useOnlineCount 怎么写订阅

useOnlineCount.ts · 核心 20 行（新 useImMessages 将完全照此范式）TypeScript
function createOnlineCountComposable() {
  const onlineUserCount = ref(0);            // 响应式状态
  const sse = useSse();                       // 拿单例连接
  let unsubscribe: (() => void) | null = null;

  const initialize = () => {
    sse.connect();                            // 确保连接（内部幂等，连着就跳过）
    unsubscribe = sse.on("online-count", (count: number) => {
      if (count !== undefined && !isNaN(count)) onlineUserCount.value = count;
    });
  };
  const cleanup = () => { unsubscribe?.(); unsubscribe = null; };  // 只退订，不关全局连接
  return { onlineUserCount: readonly(onlineUserCount), initialize, cleanup, ... };
}
// 外层 useOnlineCount() 同样做了单例 + 组件上下文内 onMounted 自动 initialize

Chapter 4 · 鉴权链路

token、@CurrentUserId、商家归属校验

客服消息涉及买卖双方，鉴权必须做到：连接能认人、接口能认人、数据能验归属。

4.1 为什么 SSE 端点在 permitAll 里

SecurityConfig.java · L31Java
"/api/user/login", "/api/v1/sse/**", ... .permitAll()

原因链条：EventSource 不能设置请求头 → 带不了 Authorization: Bearer → Spring Security 的 JWT 过滤器认不出它 → 只能放行 URL → connect() 方法内部自行解析 ?token=（2.3 节第③步）。这是 SSE/WebSocket 项目的通行做法，代价是：token 出现在 URL 里，可能进访问日志——所以 TraceFilter 已把 /api/v1/sse/ 列入噪声白名单不记录（一举两得）。

红线：新的客服业务接口（发消息/查会话等 REST）绝不放进 permitAll。它们走普通 Authorization 头，由 Spring Security 的 anyRequest().authenticated() 正常拦截。

4.2 @CurrentUserId 参数解析器

@Override
public boolean supportsParameter(MethodParameter parameter) {
    // 只处理「标了 @CurrentUserId 且类型是 Long」的参数
    return parameter.hasParameterAnnotation(CurrentUserId.class)
            && Long.class.isAssignableFrom(parameter.getParameterType());
}
@Override
public Object resolveArgument(...) {
    String authHeader = request.getHeader("Authorization");
    if (authHeader == null || !authHeader.startsWith("Bearer ")) return null;  // 未登录 → null
    try {
        return jwtUtil.getUserIdFromToken(tokenUtils.extractToken(authHeader)); // 解析失败也 → null
    } catch (Exception e) { return null; }
}

所以任何新 Controller 方法只要写 @CurrentUserId Long userId 就能拿到当前登录人 id——与项目里 MerchantController 的留言接口用法一致。注意它是「解析」不是「拦截」：真正的访问控制由 Spring Security 完成，两者分工不同。

4.3 商家归属校验：项目范式

    if (message == null || !message.getMerchantId().equals(merchantId)) {
        throw new BusinessException("留言不存在");     // 不是自己的数据，一律「不存在」

  • 为什么要二次校验：登录只证明「你是谁」，不证明「这条数据归你」。商家 B 把 URL 里的 messageId 改成商家 A 的，必须在这里拦下（水平越权）。
  • 报错话术约定：返回「不存在」而非「无权限」，不向攻击者泄露数据是否存在。
  • 新的 ChatService 对商家侧会话操作必须照抄这个模式：先 selectById 会话，再 conversation.getMerchantId().equals(merchantId)。

    `content`          VARCHAR(500) NOT NULL COMMENT '消息内容（纯文本）',
    `is_read`          TINYINT      NOT NULL DEFAULT 0 COMMENT '0未读 1已读',
    `create_time`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_conv_id` (`conversation_id`, `id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '客服聊天消息表';

四个设计决策的理由：

  • uk_user_merchant 唯一键：防止「发起会话」接口并发重复建会话；发起逻辑用「先查 → 无则插」，撞唯一键时捕获重查即可。
  • 未读数冗余在会话表（user_unread/merchant_unread）：查「会话列表 + 各会话未读数」一次查询搞定，不用对消息表做 group by count——消息表随时间膨胀后这个代价差异巨大。
  • last_message/last_msg_time 冗余：会话列表按最近消息排序是最高频查询，冗余后列表页零 join。
  • 消息表索引 (conversation_id, id)：历史消息按「会话内 id 倒序翻页」的游标分页（WHERE conversation_id=? AND id < ? ORDER BY id DESC LIMIT 20）正好命中。

注册表改造目标骨架（目标代码，实施时以此为准）：

目标代码 · SseController 改造核心（骨架）Java
// 改造前：Map<String, SseEmitter>（按连接，无法定向推）
// 改造后：userId → 该用户所有活跃连接（多 Tab 各一条，都能收到）
private final Map<Long, Set<SseEmitter>> userEmitters = new ConcurrentHashMap<>();

private void register(Long userId, SseEmitter emitter) {
    userEmitters.computeIfAbsent(userId, k -> ConcurrentHashMap.newKeySet()).add(emitter);
}
private void unregister(Long userId, SseEmitter emitter) {
    Set<SseEmitter> set = userEmitters.get(userId);
    if (set != null) {
        set.remove(emitter);
        if (set.isEmpty()) userEmitters.remove(userId);   // 防止空 Set 堆积
    }
}

// 定向推送：给某个在线用户的所有连接推同一事件；返回是否至少送达一条
public boolean sendToUser(Long userId, String eventName, Object data) {
    Set<SseEmitter> set = userEmitters.get(userId);
    if (set == null || set.isEmpty()) return false;        // 不在线 → 调用方走离线通知兜底
    boolean delivered = false;
    for (SseEmitter emitter : set) {
        try {
            emitter.send(SseEmitter.event().name(eventName)
                    .data(data, MediaType.APPLICATION_JSON));
            delivered = true;
        } catch (IOException e) {
            set.remove(emitter);                           // 死连接顺手清掉
        }
    }
    return delivered;
}

目标代码 · sendMessage 实现要点Java
@Transactional
public ChatMessage sendMessage(Long senderId, Long conversationId, String content) {
    ChatConversation conv = conversationMapper.selectById(conversationId);
    if (conv == null) throw new BusinessException("会话不存在");
    // 归属校验：发送者必须是会话双方之一（水平越权防线）
    if (!conv.getUserId().equals(senderId) && !conv.getMerchantId().equals(senderId))
        throw new BusinessException("会话不存在");

    // 1. 落库（id 自增即游标）
    ChatMessage msg = new ChatMessage().setConversationId(conversationId)
            .setSenderId(senderId).setSenderType(...).setContent(content).setIsRead(0);
    messageMapper.insert(msg);

    // 2. 更新会话冗余字段：last_message/last_msg_time/last_sender + 对方 unread+1
    boolean fromUser = conv.getUserId().equals(senderId);
    LambdaUpdateWrapper<ChatConversation> uw = new LambdaUpdateWrapper<>();
    uw.eq(ChatConversation::getId, conversationId)
      .set(ChatConversation::getLastMessage, abbreviate(content, 200))
      .set(ChatConversation::getLastSender, fromUser ? 1 : 2)
      .set(ChatConversation::getLastMsgTime, msg.getCreateTime())
      .setSql(fromUser ? "merchant_unread = merchant_unread + 1"
                       : "user_unread = user_unread + 1");
    conversationMapper.update(null, uw);

    // 3. 实时推送对方；不在线 → 离线站内信兜底（事务内 createAndPublish 与留言模块同款）
    Long receiverId = fromUser ? conv.getMerchantId() : conv.getUserId();
    boolean online = ssePushService.sendToUser(receiverId, "im-message", toPayload(msg, conv));
    if (!online) {
        noticeService.createAndPublish("您有新的客服消息", abbreviate(content, 100),
                3, receiverId, "chat_message", msg.getId());
    }
    return msg;
}

6.5 边界与取舍（必须知道的现实约束）

  • 单实例内存态：userEmitters 在 JVM 内存里。服务重启 → 全部连接断 → EventSource 自动重连恢复；会话/消息都在 MySQL，不丢数据。将来若部署多实例，需把「找用户在哪个实例」改为 Redis 注册表 + pub/sub 广播——当前 2C2G 单实例不需要做，但面试能讲清这个演进路径。
  • 消息可靠性模型是「拉兜底推加速」：SSE 只保证「在线时快」，不保证「必达」；真源在 MySQL，进会话页必拉历史消息 + 未读数，断线重连后页面刷新即对齐。这就是为什么不需要复杂的 ACK 机制。
  • Nginx 已就绪：生产配置已含 proxy_buffering off + proxy_read_timeout 3600s，前端改动零运维。
