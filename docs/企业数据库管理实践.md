# 企业数据库管理实践

> 一句话总结：**数据库管理已经从「自己搭、自己连、出问题再救」，演变为「云托管 + 堡垒机审计 + 最小权限 + 版本化变更 + 自动化备份容灾 + 指标告警」。数据是资产，一切访问与变更都要可追溯。**

---

## 1. 核心认知

大多数应届生（包括早期自己部署项目的我）对数据库管理的理解停留在：
- 装个 MySQL / 用 Navicat 连上
- root 账号直接改
- 手敲 SQL / `ALTER TABLE`
- 出问题了再看日志

但企业的生产数据库管理，重点不在「用什么工具」，而在 **「制度 + 托管 + 留痕」** 这套体系。

---

## 2. 六大管理层面

### 2.1 托管形态：优先云 RDS

| 形态 | 说明 | 适用 |
|---|---|---|
| 云 RDS（阿里云/腾讯云/TDSQL/AWS Aurora） | 备份、HA、自动扩缩容、补丁升级由云厂商负责 | 生产首选（约 90%） |
| 自托管 Docker/K8s | 自己部署、自己运维 | 学习、隔离、合规敏感场景 |

- DBA 不再碰服务器，只负责「管账号、看指标、审变更」。
- 自己 docker-compose 装 MySQL 是自托管，适合学习，生产上很少全职这么干。

### 2.2 访问控制（红线）

与个人开发最大不同：

- **绝不把数据库端口直接暴露公网**，也绝不 `Navicat → 公网IP:3306` 直接连。
- 开发连库走 **VPN / 跳板机（堡垒机 JumpServer / 阿里云 Bastionhost）**。
- 所有数据库访问有**操作审计日志**（谁、何时、执行了什么 SQL 都可追溯）。
- 来源 IP 白名单、SSH 隧道、链路加密（TLS）。

> 一句话：你能「连上」不代表该让你裸连，关键是**有没有留痕、能不能追责**。

### 2.3 权限治理：最小权限 + 账号分级

- `root` 只有 DBA 一个人持有。
- 每个同事 / 每个应用建**独立账号**，只授权它真正需要的库和权限。
- 常见分级：
  - 只读账号 → 数据分析 / 巡查
  - 应用账号 → 读写指定库，且写操作走**读写分离**（主库写、从库读）
  - 最高权限 → 仅 DBA
- Navicat 等客户端里的连接预设也会分级，**root 密码不共享**。

### 2.4 变更管理：版本化 + 评审

生产上改表结构几乎不手敲 `ALTER TABLE`：

- 用 **Flyway / Liquibase** 将 SQL 变更版本化，跟随代码走 CI/CD。
- 小表直接跑；大表用 **pt-osc / gh-ost** 在线变更，避免锁表拖垮业务。
- 上线前有评审，改库需 DBA 审批，优先可回滚。

### 2.5 数据保护：备份 + 容灾

- **定时全量备份** + **binlog 增量**，**异地 / 异机存储**。
- 主从同步（至少一主一备），或多可用区 / 跨区容灾。
- 关键：**定期做恢复演练** —— 能备份 ≠ 能恢复，恢复不出来等于没备份。
- 个人项目习惯「删库重导 dump」，生产用 **binlog 增量追平**。

### 2.6 监控运维：指标 + 告警

- 工具：Prometheus + mysqld_exporter / 云监控。
- 盯：CPU、内存、连接数、慢查询、主从延迟、复制状态，并设置告警阈值。
- 趋势类问题（容量不足、慢查询变多）靠**容量规划**提前处理，而非事发救火。
- 核心理念：**观察型 DBA，先看到数据再决策。**

## 3. 对照：当前 e-shop 个人项目 vs 企业规范

| 维度 | 个人项目现状 | 企业规范 | 主要差距 |
|---|---|---|---|
| 账号权限 | `root/123456`，3307 想公网直连 | DBA 独权 + VPN/堡垒机 + 审计 | 权限治理、访问控制 |
| 结构变更 | 手写 SQL / 直接 `ALTER` | Flyway 版本化 + DBA 评审 | 变更管理 |
| 容灾 | 首次启动导 `eshops.sql` | binlog 增量 + 恢复演练 | 容灾能力 |
| 监控 | 看日志查问题 | 指标告警 + 容量规划 | 可观测性 |

## 4. 关键术语速查

| 术语 | 含义 |
|---|---|
| RDS | 关系型云数据库托管服务（Relational Database Service） |
| DBA | 数据库管理员（Database Administrator） |
| 堡垒机 / 跳板机 | 统一入口 + 审计的访问管理设备 |
| 最小权限 | 只给完成任务所需的最少权限 |
| 主从复制 | 主库写、从库读，分担读写压力并做容灾 |
| binlog | 二进制日志，记录所有变更，用于增量备份与从库同步 |
| pt-osc / gh-ost | MySQL 在线改表结构工具，避免锁表 |
| Flyway / Liquibase | 数据库版本化迁移工具 |
| 慢查询 | 执行时间超过阈值的 SQL，是优化重点 |

---

## 5. 面试/简历可用点

- 数据库管理是「制度 + 托管 + 留痕」，数据是资产，**一切访问与变更要可追溯**。
- 企业生产不用公网裸连数据库，都是 VPN / 堡垒机 + 白名单 + 审计。
- 结构变更用 Flyway / Liquibase 版本化，大表在线变更用 gh-ost。
- 备份要异地 + 定期恢复演练；监控靠指标告警 + 容量规划而非事后救火。
- 若在简历写「数据库管理」，建议展开其中一块（如读写分离、Flyway 变更管理）讲透，比罗列多个名词更有竞争力。
