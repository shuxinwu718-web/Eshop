# 秒杀系统性能压测与优化报告

> 压测日期：2026-09-08 ｜ 环境：Windows / JDK 17 / Spring Boot 3.2 / MySQL 8 / Redis / RabbitMQ
> 测试对象：`POST /api/seckill/{sessionId}`（优惠券秒杀模式）

## 一、测试方法

| 项目 | 说明 |
|------|------|
| 工具 | JMeter 5.6.3（非 GUI 模式） |
| 并发模型 | 100 线程 × 50 循环 = 5000 请求，ramp-up 10s |
| 数据规模 | 100 个真实注册用户（token CSV），单场次限领 1 张，场次库存 100000 |
| 流量构成 | 100 个成功领取 + 4900 个重复请求拒绝（模拟真实秒杀的"极低成功率"特征） |
| 公平性 | 基线与优化后使用同一台机器、同一 JVM 启动参数（`mvn spring-boot:run`，限流关闭）、同一数据集 |
| 预热 | 优化后测试前执行 3 轮预热压测（排除 JIT 冷启动干扰） |
| 一致性验证 | 压测后核对 DB 库存、Redis 库存、`user_coupon` 记录三方一致 |

## 二、压测结果对比

| 指标 | 基线（优化前） | 优化后 | 变化 |
|------|--------------|--------|------|
| **吞吐量 QPS** | 217.9 | **365.9** | **+68%** |
| **平均响应** | 359 ms | **90 ms** | **-75%** |
| P50 | 301 ms | 89 ms | -70% |
| P90 | 479 ms | 133 ms | -72% |
| P95 | 601 ms | 147 ms | -76% |
| **P99（尾延迟）** | 2,425 ms | **174 ms** | **-93%** |
| Max | 3,092 ms | 232 ms | -93% |
| 超卖 | 无 | 无 | ✅ |

关键结论：
- **尾延迟（P99/Max）坍缩了 93%**——高并发下的长尾来自锁竞争与连接池排队，优化后消失；
- 单请求服务端处理成本从 **46ms 降至 23ms**（单线程隔离测量）；
- 拒绝路径（占请求量 98%）不再触碰数据库，重复请求被轻量拦截。

## 三、一致性（防超卖）验证

```
场次库存剩余   = 99900   （100000 - 100，与成功领取数严格一致）
券领取总数     = 100
去重用户数     = 100     （Redis SET 判重生效，无重复领取）
空用户/脏数据  = 0
```

Redis 预扣库存、DB 库存、发放券记录三方对账一致，**零超卖、零少卖**。

## 四、优化项清单（按收益排序）

### 1. JwtParser 复用 —— jstack 实证的最大隐藏瓶颈（单请求 46ms → 23ms）

**现象**：压测中抓取 jstack，发现 35/104 个 Tomcat 工作线程阻塞在
`io.jsonwebtoken.impl.lang.Services.loadFirst → JarURLConnection → JarFileFactory`。

**根因**：原实现在每个请求中调用 4~5 次 `Jwts.parserBuilder().build()`（validate / userId / username / sver 各解析一次）。
jjwt **每次 build 都会执行 ServiceLoader 扫描全 classpath 的 `META-INF/services/`**——逐个打开 100+ 个 JAR 文件，
且 `JarFileFactory` 内部有同步锁，高并发下线程在此排队并触发大量 Windows 文件系统调用。

**修复**：`JwtUtil` 中 parser 改为 `@PostConstruct` 构建一次全局复用（构建后不可变、线程安全），
每请求 4~5 次 JAR 扫描 → 0 次。签名校验逻辑不变，无安全语义变化。

> 面试点：性能问题不要猜，用线程转储看线程真实阻塞点；"每个请求 new 一个 parser"是 jjwt 官方文档明确警示的反模式。

### 2. 事务边界收窄 —— 拒绝流量不再占用数据库连接

**根因**：原实现 `@Transactional` 标注在整个 `seckill()` 方法上，98% 被拒绝的请求
（重复/售罄）也要先从 HikariCP（默认 10 连接）借出连接、开启空事务再回滚——
洪峰下连接池被无效流量占满，所有请求排队等连接。

**修复**：主流程去除 `@Transactional`，仅落库段（扣库存 + 写记录）用编程式事务
`TransactionTemplate.executeWithoutResult` 包裹。失败时事务回滚 + Redis 抢占回滚（`rollbackClaim`），
一致性语义与原实现完全等价。

### 3. Lua 原子抢购 —— 3 次 Redis RTT 合并为 1 次

判重（SISMEMBER）+ 扣库存（DECR）+ 记录用户（SADD）在服务端多次往返之间存在竞态窗口。
合并为一段 Lua 脚本（`scripts/seckill_claim.lua`）单次执行：
- 1 次 RTT 完成"检查-扣减-记录"，天然原子，杜绝"扣了库存没记录用户"类中间态；
- 库存不足时脚本内 `INCR` 回补，不产生脏状态。

### 4. 本地售罄标记 + Caffeine 元数据缓存

- `localSoldOut`（ConcurrentHashMap）：Lua 返回售罄后置位，后续售罄请求 O(1) 拒绝，
  连 Redis 都不打（本场测试中该路径未触发，因库存充足；这是真实秒杀洪峰的主力防线）；
- 场次（5s TTL）/ 优惠券（30s）/ 商品（10s）元数据进 Caffeine 本地缓存，
  `Optional` 缓存空值防穿透；元数据变更时主动失效并同步清理售罄标记。

### 5. 拒绝路径日志降噪

每个被拒绝请求原先产生 2 条 WARN（Service 层 + 全局异常处理器），同步 ConsoleAppender
在洪峰下形成写锁串行化。高频预期拒绝降级为 `debug`（生产 info 级别不输出），
异常处理器保留 error/warn 语义不变。

### 6. 限流器 Lua 原子化（修复 INCR+EXPIRE 竞态）

原"先 INCR 再 EXPIRE"两步执行，进程在两步之间崩溃会留下**永不过期的计数键**（用户被永久限流）。
改为一段 Lua（INCR 后仅当返回 1 时 EXPIRE），限流参数外置到 `application.yml` 可热调。

## 六、后续优化方向（Next Steps）

1. **公共链路**：TraceFilter 每请求同步发送 RabbitMQ 访问日志，现已与 seckill 路径持平成为新瓶颈
   （公共端点对照实验 363/s）——可改批量/异步队列化，预期再上一个台阶；
2. **用户信息缓存**：`loadUserByUsername` 每请求查库，可加短 TTL 缓存（安全语义：角色变更延迟生效需评估）；
3. **分布式扩展**：库存分桶（将一个大 key 拆为 N 个分段库存）提升 Redis 单 key 热点上限；
4. **压测环境**：客户端与服务器同机存在资源竞争，生产级数据建议独立压测机。
